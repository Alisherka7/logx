> mean the application already follows these rules, and LogX has not changed any application

## 1. Use the existing logging framework

- Keep using the framework the project already has. For standard-library `logging`, each module
  gets its own logger: `logger = logging.getLogger(__name__)`.
- Configure handlers and formatters once, at application startup (for example in the FastAPI
  app factory or entry point), never in library modules.
- Reserve `print()` for intentional command-line output.

## 2. Structured logs in production

- In production, emit one structured record (for example JSON) per line to stdout/stderr, so the
  platform's log collector can parse it.
- Write messages as stable event descriptions and pass variable data as fields, not as text
  baked into the message: `logger.info("order created", extra={"order_id": order.id})`.
- Choose levels deliberately: `DEBUG` for diagnostics, `INFO` for notable business events,
  `WARNING` for recoverable problems, `ERROR` for failures that need attention.

## 3. Readable output in development

- In local development, use a human-readable formatter (timestamp, level, logger name, message).
- Select the format from configuration (for example an environment variable), not by editing code.

## 4. Request and task context

- Attach a request ID (or task/job ID) to every log record produced while handling a request
  or background task, for example via a `contextvars.ContextVar` set in FastAPI middleware plus
  a `logging.Filter` that copies it onto records.
- Propagate an incoming request ID header when one is present; otherwise generate one.

## 5. Exceptions

- Inside `except` blocks, log with `logger.exception(...)` or pass `exc_info=True` so the
  traceback is kept. Logging only `str(exc)` loses where the error happened.
- Log an exception once, where it is handled, rather than at every layer that re-raises it.
- Do not silently discard exceptions (`except ...: pass`). If suppression is intended, narrow the
  exception type and leave a comment explaining why.

## 6. Sensitive data

- Never log secrets, credentials, tokens, session cookies, full payment data, or full request
  bodies. Be deliberate about personal data (emails, names, addresses, IP addresses).
- Prefer logging identifiers (user ID, order ID) over the underlying personal data.
- LogX does **not** detect sensitive-data leaks; reviews remain a human responsibility.

## Checking

Run `logx check` to find a few common, mechanically detectable issues (direct `print`,
exceptions logged without tracebacks, silently discarded exceptions). Findings are review
candidates; passing the check does not mean these conventions are followed.
